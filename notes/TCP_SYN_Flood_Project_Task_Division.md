# TCP SYN Flood Project — Equal Task Division for Two Persons

## Project Goal

The project demonstrates a **TCP SYN flood attack in an isolated laboratory network**, measures its effect on a target TCP server, and evaluates defenses such as **SYN cookies and rate limiting**.

The project uses three logical machines:

- **VM 1:** SYN traffic generator
- **VM 2:** Target TCP server
- **VM 3:** Legitimate client + monitoring

To keep the workload balanced, both members have one major implementation responsibility, one major experimental responsibility, and one documentation/presentation responsibility.

---

# Person 1 — Attack Tool and Traffic Generation

## 1. Set Up the Attacker / Generator VM

Person 1 will prepare **VM 1**.

### Tasks

- Install Ubuntu or Kali Linux.
- Configure the VM on the isolated/host-only network.
- Assign an address such as:

```text
192.168.56.10
```

- Verify connectivity with the target VM.
- Install the libraries/tools needed for packet generation and packet inspection.

### Deliverable

A working attacker VM that can communicate only with the laboratory network.

---

## 2. Develop the TCP SYN Generator

Person 1 will implement the main SYN-generation tool.

The program should accept parameters such as:

```text
Target IP
Target port
Packet rate
Experiment duration
```

### Required Features

- Construct TCP SYN packets.
- Send them toward the authorized target.
- Allow the sending rate to be configured.
- Automatically stop after the configured duration.
- Count the number of transmitted packets.
- Print a short experiment summary.
- Restrict the program to the laboratory target/subnet.

### Example Program Flow

```text
Read target IP
Read target port
Read packet rate
Read duration

Validate target

Start timer

while duration has not expired:
    create SYN packet
    send SYN packet
    increment counter
    enforce configured rate

Stop
Print statistics
```

### Deliverable

A working SYN-generation program for controlled experiments.

---

## 3. Validate Generated Packets

Person 1 will verify that the generator produces the intended TCP packets.

Use:

- Wireshark
- tcpdump

Confirm that the generated packets contain:

```text
SYN = 1
ACK = 0
```

and are directed toward the selected TCP service.

### Deliverable

Packet-capture evidence showing the SYN packets generated by the tool.

---

## 4. Perform Attack-Side Experiments

Person 1 will run controlled experiments at several traffic levels.

Suggested experimental stages:

```text
Baseline
Low SYN load
Medium SYN load
Higher authorized laboratory load
```

For each run, Person 1 should record:

- Configured SYN rate
- Experiment duration
- Number of packets transmitted
- Start/end time
- Any observed generator-side errors

### Deliverable

An attack-side results table.

Example:

| Test | Configured Load | Duration | SYN Packets Sent |
|---|---:|---:|---:|
| T1 | Baseline | 30 s | 0 |
| T2 | Low | 30 s | Measured value |
| T3 | Medium | 30 s | Measured value |
| T4 | Higher lab load | 30 s | Measured value |

---

## 5. Attack-Side Documentation

Person 1 will prepare the report/presentation material for:

- TCP SYN flood mechanism
- TCP three-way handshake
- Why half-open connections occur
- SYN generator design
- Packet/header fields used by the project
- Attack timing diagram
- Screenshots of generated SYN traffic

# Person 2 — Target, Monitoring, Measurement, and Defense

## 1. Set Up the Target Server VM

Person 2 will prepare **VM 2**.

### Tasks

- Install Ubuntu Linux.
- Configure the VM on the isolated network.
- Assign an address such as:

```text
192.168.56.20
```

- Install a harmless TCP service such as Nginx.
- Verify that the service is reachable from the legitimate client.

Example service:

```text
HTTP / TCP port 80
```

### Deliverable

A functioning TCP server that can be used as the laboratory target.

---

## 2. Set Up the Legitimate Client / Monitoring VM

Person 2 will also prepare **VM 3**.

Example address:

```text
192.168.56.30
```

This VM will:

- Act as a legitimate user.
- Connect normally to the target server.
- Measure connection time.
- Record success/failure.
- Capture traffic if required.

### Deliverable

A working legitimate-client and monitoring environment.

---

## 3. Collect Baseline Measurements

Before the SYN generator is started, Person 2 will measure normal behavior.

Record:

- Normal TCP/HTTP connection latency
- Legitimate connection success rate
- Number of TCP connections
- CPU usage
- Memory usage
- Number of `SYN-RECV` connections

Useful tools include:

```bash
ss -ant
```

```bash
time curl http://192.168.56.20
```

```bash
top
```

or:

```bash
htop
```

### Deliverable

A baseline-results table.

---

## 4. Monitor the Target During SYN Experiments

While Person 1 runs the SYN generator, Person 2 will monitor the target.

Observe:

- Incoming SYN traffic
- SYN-ACK responses
- `SYN-RECV` connections
- Legitimate connection latency
- Connection success/failure
- CPU and memory utilization

Person 2 should also capture the normal and abnormal TCP behavior using Wireshark or tcpdump.

### Important Evidence

The project should demonstrate this relationship:

```text
Increasing SYN traffic
        ↓
More incomplete TCP handshakes
        ↓
More SYN-RECV / backlog pressure
        ↓
Higher legitimate-client latency
        ↓
Possible connection failures/timeouts
```

### Deliverable

Target-side packet captures and measurements for every test level.

---

## 5. Implement and Evaluate Defenses

Person 2 will implement the defense portion.

Primary defense:

- **SYN cookies**

Possible additional defense:

- SYN rate limiting
- Firewall filtering
- TCP backlog tuning

Check the SYN-cookie setting using:

```bash
sysctl net.ipv4.tcp_syncookies
```

Then repeat the same experiment using the same traffic level.

Compare:

```text
Without defense
vs.
With defense
```

Measure:

- Number of half-open connections
- Legitimate connection success rate
- Legitimate connection latency
- Server resource usage

### Deliverable

A defense-comparison table.

Example:

| Configuration | SYN Load | SYN-RECV | Client Success | Avg. Latency |
|---|---:|---:|---:|---:|
| Without defense | Same test load | Measured | Measured | Measured |
| With defense | Same test load | Measured | Measured | Measured |

---

## 6. Defense and Result Documentation

Person 2 will prepare report/presentation material for:

- Target-server architecture
- Monitoring methodology
- Experimental metrics
- SYN cookies
- Other defense ideas
- Before/after defense comparison
- Graphs and result analysis

# Shared Tasks

The following tasks should be completed together.

## 1. Network Integration

Both members verify:

```text
VM 1 — Generator
192.168.56.10

VM 2 — Target
192.168.56.20

VM 3 — Client/Monitor
192.168.56.30
```

All three machines must be connected only through the isolated laboratory network.

---

## 2. Final Experimental Runs

Both members should be present for the final runs.

For every test:

1. Person 2 starts monitoring.
2. Person 2 starts legitimate-client measurements.
3. Person 1 starts the SYN generator.
4. Person 1 records generator statistics.
5. Person 2 records target behavior.
6. Both verify the packet capture.
7. Results are saved before moving to the next test.

This avoids mismatched timing or incomplete measurements.

| Defense | Assist repeat tests | Main implementation |
| Graph | Latency-related graph | Success/defense-related graph |
| Report | Attack/design sections | Results/defense sections |
| Presentation | Attack side | Target/defense side |
| Final integration | Shared | Shared |

Although Person 2 configures two VMs, those machines require relatively little custom programming. Person 1 carries the larger coding responsibility by implementing the SYN-generation tool. This keeps the overall workload approximately equal.
